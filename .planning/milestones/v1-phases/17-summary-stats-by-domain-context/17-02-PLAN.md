<objective>
Wave 1 (spec §5). Build the extended analysis dataset per locked decision D-01, match every
column against the PRECEDE dictionary, assign each documented variable to exactly one clinical
domain (D1-D5) or OUT_OF_SCOPE, decide its stat_route (MEANS or FREQ) from type AND cardinality,
and record a one-line domain_rationale for every assigned variable citing which of the three
assignment rules applied. Persist the result as g.var_domain_map and export it for Gerard's
variable-by-variable review (Checkpoint 1). No statistics run until that review is approved.

Purpose: The domain map is the spine of the whole phase. A wrong domain, a blank rationale, or a
mis-routed variable propagates into every downstream sheet. D-01's join is where the key type
conflict must be neutralized or D3/frailty columns come back silently all-missing — and the cast
must be generated at MACRO time from dictionary metadata, because a DATA step compiles both
branches of a runtime `vtype()` test and will fail to compile on the branch that does not apply.
Two further traps live here: an identifier routed to PROC FREQ produces a 41,000-level table and
an unusable sheet, and a numeric-coded categorical (30-day mortality, sex, ASA class) routed to
PROC MEANS reports a meaningless mean instead of a level/n/% table.
Output: sas/17_summary_stats_by_domain.sas Sections 1-4, g.var_domain_map, and
qc/17_var_domain_map_review.csv. Ends at a blocking human checkpoint.
</objective>

1. KEY UNIQUENESS GATE (before any merge). A DATA step merge silently becomes a match-merge if the
   extension side has duplicate keys. The post-merge row-count assertion in step 5 would catch the
   row inflation, but it reports "41,153 ne 41,150" rather than naming the problem. Assert first:
   `proc sql noprint; select count(*) into :n_key_dups trimmed from (select PRECEDE_STUDY_ID from g.master_data_merged group by PRECEDE_STUDY_ID having count(*) > 1); quit;`
   `%macro check_key_unique; %if &n_key_dups > 0 %then %do; %fail_out(msg=&n_key_dups duplicate PRECEDE_STUDY_ID values in g.master_data_merged -- extension merge requires a unique key or an explicit collapse rule); %end; %mend check_key_unique; %check_key_unique;`

2. MACRO-TIME KEY TYPE RESOLUTION. Read the stored type of PRECEDE_STUDY_ID from dictionary.columns
   into a macro variable, then generate the cast from it. Do NOT write a runtime `vtype()` branch:
   SAS compiles both branches of a DATA step IF regardless of which one executes, so
   `put(PRECEDE_STUDY_ID, best12.)` against a character variable is a compile-time error and the
   step never runs. Note for the record: a SAS variable has exactly one type per dataset — the md7
   numeric-key history describes the SOURCE files, not g.master_data_merged, which holds a single
   resolved type.
   `proc sql noprint; select type into :key_type_merged trimmed from dictionary.columns where libname='G' and memname='MASTER_DATA_MERGED' and upcase(name)='PRECEDE_STUDY_ID'; quit;`

3. Read the extension columns from g.master_data_merged into a work copy, casting the key to
   CHAR $12, using EXACTLY the KEEP= list recorded in 17-01-SUMMARY.md (frailty score, frailty
   components, cognitive score, intraop-physiologic block; PRECEDE_STUDY_ID_1 excluded). Prefer
   building the list dynamically from work.ext_candidates left in WORK by Wave 0
   (`select name into :extension_keep_list separated by ' ' from work.ext_candidates;`) over
   transcribing it by hand:
```sas
%macro build_ext_cols;
  data work.merged_ext_cols;
    set g.master_data_merged (keep=PRECEDE_STUDY_ID &extension_keep_list);
    length key_char $12;
    %if &key_type_merged = num %then %do;
      key_char = strip(put(PRECEDE_STUDY_ID, best12.));
    %end;
    %else %do;
      key_char = strip(PRECEDE_STUDY_ID);
    %end;
    drop PRECEDE_STUDY_ID;
    rename key_char = PRECEDE_STUDY_ID;
  run;
%mend build_ext_cols;
%build_ext_cols;
```

   key in g.analysis_base is zero-padded. `z12.` pads to twelve digits, so a numeric 123456789
   becomes '000123456789' while the character side holds '123456789' — the merge then matches
   nothing, the row count still passes, and every extension column comes back missing. That is
   exactly the silent failure Pitfall 1 describes.

4. Sort both inputs by PRECEDE_STUDY_ID: `proc sort data=work.merged_ext_cols; by PRECEDE_STUDY_ID; run;`
   and `proc sort data=g.analysis_base out=work.analysis_base_sorted; by PRECEDE_STUDY_ID; run;`

   `data work.analysis_base_ext; merge work.analysis_base_sorted (in=inbase) work.merged_ext_cols; by PRECEDE_STUDY_ID; if inbase; run;`

5. Assert the join did not lose or add rows AND that the extension actually populated (guards

   macro calling %fail_out on mismatch; count non-missing of the cognitive score column into
   :n_cog_nonmiss and %fail_out if it is 0 (a 0 means the key cast silently failed).

6. COVERAGE / DENOMINATOR CAPTURE. A non-zero cognitive count proves the join worked but says
   nothing about whether cognitive assessment covers the whole base. Compute, for each extension
   column, non-missing N in work.analysis_base_ext into work.ext_coverage (varname, n_nonmiss,
   pct_of_base). If the coverage verdict from 17-01-SUMMARY.md is PARTIAL, set a macro variable
   `%let D3_DENOM_NOTE = D3 and the D2 frailty block are computed on the subcohort with a
   non-missing assessment (n=&n_cog_nonmiss), not on the &n_base_rows base;` and carry it into

   sheet and the affected domain sheets. Without this, D3 reads as ~95 percent missing against a
   denominator that does not apply to it.
