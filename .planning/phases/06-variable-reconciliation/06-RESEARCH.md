**Primary recommendation:** Write a lightweight `06_reconcile.sas` that produces a

### The only open item: PCM-D-10

`rt_ANCHOR_to_ADMIT_days`, `rt_ANCHOR_to_SURGERY_days`, and `rt_ANCHOR_to_DISCHG_days`
are date offsets from an anchor date, not durations. A negative value means the event
preceded the anchor — this is legitimate and must NOT be nulled.

PREP-09 (03-06) scans every other `rt_*` numeric variable and writes a per-source
negative count to `logs/03_negtime_mdN.txt`. The triage rule for PCM-D-10 is:

- If the variable is one of the three rt_ANCHOR_to_*_days variables: negatives are
  expected and correct. No action.
- If the variable is a `*_mins` duration with negatives: apply the same judgment as
  PREP-08. A negative duration is invalid unless there is a documented reason (e.g.,
  a percutaneous procedure where the timestamps are defaulted). Decision: null or retain
  with documentation. Record in DECISIONS.md under PCM-D-10.
- If the variable shows zero negatives: no action needed. Record "zero negatives confirmed"
  in PCM-D-10.

The PREP-09 report from md3 (which owns the affected variables in the merge) is the
authoritative source for this triage.

## Architecture for the Phase 6 SAS Program

Phase 6 needs one SAS program: `06_reconcile.sas`.

### What 06_reconcile.sas does

This program does NOT modify any dataset. It reads `g.master_data_merged` and produces
a human-readable QC summary at `qc/06_reconcile_summary.txt`. This gives the phase an
executable artifact, keeps it consistent with the rest of the pipeline, and produces
something that `99_run_all.sas` can call.

**SECTION 0 — Preconditions**
- Assert g library accessible (same pattern as 05_qc_merge.sas SECTION 0)
- Assert g.master_data_merged exists
- Assert XCMD available for the FILE/PUT output path

**SECTION 1 — Column presence checks (REC-01, REC-02, REC-03)**

Verify that each of the sixteen deliberately-separate columns is present in the merged
file. Use `dictionary.columns` — the same mechanism as QC-02 and QC-04.

Columns to check:
- Mortality: `Death_Date_Y_N`, `IsDead_Y_N`, `Death` (PCM-D-01)
- Frailty (char): `Feels_Exausted`, `Low_Physical_Activity`, `Slow_Walking_Speed`,
  `Unintended_Weight_Loss`, `Week_Grip_Strength` (PCM-D-02, md6/md7 owners)
- Frailty (numeric): `Feels_Exausted_Value`, `Low_Physical_Activity_Value`,
  `Slow_Walking_Speed_Value`, `Unintended_Weight_Loss_Value`, `Week_Grip_Strength_Value`
  (PCM-D-02, md3/md5 owners)
- ISO_SEV: `ISO_SEV_Exp_IntraOp_MAC_Average`, `ISO_SEV_IntraOp_MAC_Average`,
  `ISO_SEV_MAC_TOTAL_Exp` (PCM-D-03)
- Derived flag: `rt_envelope_flag` (MRG-05 / PCM-D-08)
- Emergent: `Emergent` (PCM-D-04)

Pattern (using %macro assert_col_present or inline PROC SQL into :n check):

```sas
proc sql noprint;
  select count(*) into :n_death_date_yn trimmed
  from dictionary.columns
  where libname = 'G'
    and upcase(memname) = 'MASTER_DATA_MERGED'
    and upcase(name) = 'DEATH_DATE_Y_N';
quit;
%if &n_death_date_yn = 0 %then %do;
  %put ERROR: REC-01 -- Death_Date_Y_N absent from g.master_data_merged;
  %abort cancel;
%end;
```

**SECTION 2 — Emergent counts (REC-04)**

**`Emergent` is `Y` / `N` / blank -- NOT `1` / `0`.** PCM-F-06 established this: md1 and md8
both carry Y/N/blank at matching rates. An earlier draft of this document said "count positive
(= '1' or = 1)", which returns 0 for both counts and produces a summary reading
"0 positive / 0 zero" that looks like a finding rather than a coding error.

`Emergent` is also definitively CHARACTER: md3 owns it and Phase 4's LENGTH block declares it
`$1`. No type branching is needed.

```sas
proc sql noprint;
  select sum(Emergent is not missing and upcase(Emergent) = 'Y') into :n_emergent_y    trimmed,
         sum(Emergent is not missing and upcase(Emergent) = 'N') into :n_emergent_n    trimmed,
         sum(missing(Emergent))                                  into :n_emergent_miss trimmed
  from g.master_data_merged;
quit;
```

Guard: `Emergent IS NOT MISSING` before comparison (PCM-T-11).

**SECTION 3 — rt_envelope_flag distribution (MRG-05 / PCM-D-08)**

Count `rt_envelope_flag = 0` and `rt_envelope_flag = 1`. **Report both; assert NEITHER.**

An earlier draft of this document said to assert the `= 1` count matches the 9 established in
Phase 5 QC-06. Do not. 9 is a current observation, not a pipeline invariant -- a future
re-extract could legitimately produce a different number, and asserting it would turn a data
change into a pipeline abort. Phase 5's QC-06 already asserts the thing that IS invariant:
zero UNFLAGGED violations. Phase 6 only documents the distribution.

**SECTION 4 — PCM-D-10 resolution (PCM-D-10)**

This section runs only if `logs/03_negtime_md3.txt` exists (meaning 03-06 has run). It
reads the file and writes the relevant findings to the summary. No data modification.

Alternative: if PCM-D-10 triage is documented in DECISIONS.md before Phase 6 runs, this
section just confirms the agreed-upon variables have the correct null count by reading
`g.master_data_merged` directly — using the same guarded pattern as PREP-09.

**SECTION 5 — Write summary and close**

FILE / PUT the summary to `&qc_path.\06_reconcile_summary.txt`. Include:
- Run timestamp
- Column presence: PASS/FAIL for each of the sixteen columns
- Emergent count (positive / zero / missing)
- rt_envelope_flag = 1 count (expect 9)
- PCM-D-10 status

## Common Pitfalls

### Pitfall 1: Extending PREP-08 nulling to rt_ANCHOR_to_*_days
**What goes wrong:** The PREP-09 report shows negatives in anchor-offset variables. A
future maintainer interprets this as "more variables need nulling."
**Why it happens:** The `rt_` prefix pattern looks uniform; the semantic distinction
between a duration and an offset is not obvious from the name alone.
**How to avoid:** The PCM-D-10 DECISIONS.md entry must explicitly name the anchor-offset
variables and state that their negatives are valid. Include this in the 06_reconcile
QC summary output as a prominent note.

### Pitfall 2: Editing the OWN-03 generated block in docs/DECISIONS.md
**What goes wrong:** The OWN-03 block in DECISIONS.md is tagged as machine-generated
(`<!-- generated by 02_ownership.sas Plan 02 - do not hand-edit the generated block -->`).
Editing it manually creates a divergence from what the ownership program would regenerate
if run again.
**How to avoid:** Leave the OWN-03 block untouched. PCM-D-01/-02/-03 resolutions are
already written in the freeform "Resolutions -- 2026-08-27" section of DECISIONS.md,
which is the authoritative human-readable record. The data dictionary is the right place
for the column-level documentation.

### Pitfall 3: Treating Phase 6 as requiring schema changes
**What goes wrong:** Phase 6's name ("Variable Reconciliation") sounds like it might
mean renaming columns or restructuring g.master_data_merged.
**What's correct:** The "reconciliation" is a DOCUMENTATION decision — keep-separate is
the resolution for D-01, D-02, D-03. No column is renamed, dropped, or added in this
phase. The schema is unchanged from Phase 5 output.

### Pitfall 4: Asserting rt_envelope_flag = 1 count without accounting for re-run
**What goes wrong:** The hardcoded assertion `expect 9` is correct for the 2026-08-27
execution. If 03-06 re-runs and the merge re-runs (e.g., to fix something else), the 9
could change if the source data changes.
**How to avoid:** Log the count and assert zero UNFLAGGED violations (as QC-06 does);
do not hard-assert the flagged count in 06_reconcile.sas. The 9 is a current finding,
not a pipeline invariant.

## Code Examples

### Column presence check pattern (from QC-04 conventions)

```sas
/* REC-01: confirm all three mortality columns present */
%macro assert_col(lib=, dsn=, col=, label=);
  %local n;
  proc sql noprint;
    select count(*) into :n trimmed
    from dictionary.columns
    where libname = upcase("&lib")
      and upcase(memname) = upcase("&dsn")
      and upcase(name) = upcase("&col");
  quit;
  %if &n = 0 %then %do;
    %put ERROR: &label -- &col absent from &lib..&dsn;
    %abort cancel;
  %end;
  %else %put NOTE: &label OK -- &col present in &lib..&dsn;
%mend assert_col;

%assert_col(lib=G, dsn=MASTER_DATA_MERGED, col=Death_Date_Y_N, label=REC-01);
%assert_col(lib=G, dsn=MASTER_DATA_MERGED, col=IsDead_Y_N,     label=REC-01);
%assert_col(lib=G, dsn=MASTER_DATA_MERGED, col=Death,          label=REC-01);
```

### Emergent count pattern (guarded, PCM-T-11)

```sas
proc sql noprint;
```

## Open Questions

1. **Does 06_reconcile.sas need to produce the full data dictionary, or just QC summaries?**
   - What we know: Phase 8 ROADMAP lists `08_dictionary.sas` as the program that produces
     `docs/DATA_DICTIONARY.xlsx`. DOC-01 is a Phase 8 requirement.
   - What's unclear: whether Phase 6 should produce a partial dictionary (just the five

   - Recommendation: Phase 6 produces a committed prose note
     (`docs/data_dictionary_notes.md` or similar) that documents the five concept groups,
     then Phase 8 incorporates them into the XLSX. This separates the documentation
     decision (Phase 6) from the formatting work (Phase 8).

2. **Is `Emergent` a character or numeric variable in g.master_data_merged?**
   - What we know: it appears in the OWN-03 conflict list across eight sources but its
     type is not specified in any planning document.
   - RESOLVED: neither. `Emergent` is CHARACTER `$1` (md3-owned, declared in Phase 4's LENGTH
     block) and its values are `Y` / `N` / blank (PCM-F-06). Use `upcase(Emergent) = 'Y'`.
   - Recommendation: the plan task should read `dictionary.columns` for Emergent's type
     before writing the count query, or use a `%if` branch.

3. **Does PCM-D-10 require a PREP-08-style fix for any additional rt_*_mins variables?**
   - What we know: PREP-09 report does not yet exist (03-06 pending). The triage rule
     is documented above.
   - Recommendation: gate the PCM-D-10 plan task as a human-verify checkpoint that
     reads the report, decides, and records in DECISIONS.md. If additional nulling is
     needed, it would require re-running Phase 3 → Phase 4 → Phase 5 again (same chain
